# Scoring

Status: implemented 2026-09-06. Errata below each decision they correct. Written 2026-09-05.

Daily bars become percentiles, pillar scores and a dated snapshot: `metric_daily`,
`peer_group_stat`, `pillar_score_daily` and `snapshot_daily`, stamped with a versioned
`scoring_run`. Standing decisions live in `DESIGN.md`; the schema is
`docs/specs/2026-09-04-database-schema-design.md`; the securities come from
`docs/specs/2026-09-05-universe-and-identity.md` and the bars from
`docs/specs/2026-09-05-price-ingest.md`.

Scope: the whole scoring pipeline, carrying **one pillar**. Prices give Momentum and nothing
else; Valuation, Quality, Sentiment and Insider all need fundamentals, which are the next ingest
cycle. The machinery built here — adjustment, percentiles, coverage, blending, versioning — is
what those pillars will slot into without a migration.

---

## 1. What this has to satisfy

1. **Percentiles are computed within a sector peer group.** 15x P/E means opposite things for a
   utility and a chipmaker, and the same is true of a 40% twelve-month return.
2. **A score must trace back to visible raw inputs.** `metric_daily` stores the raw value beside
   its percentile so an alert can distinguish "this moved" from "its peers moved".
3. **Corporate actions must not read as performance.** Raw prices are stored unadjusted by
   design, so adjustment happens here or a 2-for-1 split becomes a −50% twelve-month return.
4. **A missing metric is dropped, never imputed**, and the resulting coverage is recorded.
5. **Scores are versioned, not overwritten.** A corrected score lands as a new run beside the
   old one, because a crossing is a property of an adjacent pair.
6. **One HTTP client, one driver.** No new runtime dependencies; scoring opens no sockets at
   all.

## 2. Decisions

D-numbers below belong to this spec. References to the schema spec's own decisions are written
`schema D<n>`.

**D1 — The full chain ships, with alerting switched off.** `metric_daily` →
`pillar_score_daily` → `snapshot_daily`, under a weight version of `{Momentum: 1.0}`.

A blended score derived from one pillar is the momentum score wearing a suit, and the design
refuses to hide that: `snapshot_daily.min_coverage` and `pillar_agreement` state it on every row.

**`scoring_run.emits_alerts` is `false` for every run this cycle produces**, and the reason is
not that a one-pillar blend is embarrassing. Nothing reads that flag yet — no crossing diff, no
cooldown, no Discord POST exists — so it is a claim recorded for the alerting cycle to honour
later, and the question it answers is whether *that* cycle should treat these runs as
alert-worthy when it looks back at them. Three reasons it should not:

- **The suppression machinery does not exist.** `DESIGN.md` requires deduplication and a
  per-ticker cooldown "from day one" precisely because a score hovering near a threshold
  otherwise fires nightly and the channel is muted within a week. Runs marked alert-worthy
  before any of that is built would hand the first alerting run a backlog computed without it.
- **These scores are not comparable to what follows.** Fundamentals arriving is a
  `scoring_logic_version` bump, and two scores are comparable only under the same logic and
  weight version. Every crossing from the momentum-only era is incomparable with everything
  after it, so alerting on them would tune thresholds against a regime about to cease existing.
- **The alert would restate itself.** `DESIGN.md`'s worked example — "NVDA 68 -> 82. Quality 91,
  Valuation 44, Momentum 88. Driver: three upward revisions in 5 days" — collapses to "NVDA
  68 -> 82. Momentum 82" with one pillar. And the design's own claim is that strength in three
  pillars at once is rarer and more interesting than a top decile in one, which makes a
  one-pillar crossing definitionally the least interesting case there is.

The test for flipping it is therefore not "does the labelling look honest now". It is: does
deduplication and cooldown exist, and is the scoring regime the one that will still be running
afterwards. Both belong to the alerting cycle.

Stopping at `pillar_score_daily` was considered and rejected. It is marginally more honest and
materially worse: the dashboard would read a shape it has to abandon later, and the crossing
diff would have nothing to be built against, so the alerting cycle would land untested.

**D2 — Forward-only. This cycle emits no historical scores.** Score today, then once a night.

The schema already says so: `price_daily` has partitions pre-created back to 2020, while every
derived table has only 2026. Six years of prices are the *trailing input* every momentum metric
reads, not a mandate to emit six years of snapshots.

Backfilling to 2021 would mean roughly 2.1M `snapshot_daily` rows and 8.4M `metric_daily` rows,
partitions that do not exist, and a lookahead that would have to be stated in every result: only
today's sector labels are held, so a 2022 percentile would be computed against 2026's peer
groups. `scoring_run.status` already carries a `backfill` value, so this stays a run type to add
later rather than a redesign.

**D3 — Total return, not price return.** Splits *and* dividends fold into one cumulative
adjustment factor. `corporate_action` stores dividends as well as splits, and if only splits
mattered at scoring time the 25,455 dividend rows already ingested would have no consumer. The
split half has to be built correctly regardless, so dividends ride the same machinery.

**D4 — Back-adjustment, anchored at the present.**

```
adjusted_close(t) = raw_close(t) × Π factors for every action with effective_date > t

    split, ratio r        factor = 1 / r
    dividend, amount D    factor = (P − D) / P,  P = close on the bar before the ex-date
```

Anchored at the present so the most recent price is the one that needs no adjustment, which is
the price a reader recognises. This is the one piece of arithmetic in the cycle where a wrong
answer looks entirely plausible, so it is a pure function with its own tests.

**D5 — Four metrics, all higher-is-better.**

| code | definition |
|---|---|
| `ret_3m` | adjusted close ÷ adjusted close ~3 calendar months back − 1 |
| `ret_6m` | same, 6 months |
| `ret_12m` | same, 12 months |
| `off_52w_high` | adjusted close ÷ max adjusted close over 52 weeks − 1 |

Calendar months rather than session counts, taking the nearest bar at or before the target date:
that survives holidays without a market calendar, and "three-month return" means the calendar
thing to a human. `off_52w_high` is ≤ 0, with 0 meaning *at* the high.

**Plain twelve-month, not 12-minus-1.** Momentum research conventionally skips the most recent
month, because short-term reversal makes it negatively predictive. Rejected here for consistency:
one of four metrics defined differently from its siblings would be misread by whoever looks next,
`DESIGN.md` says plain twelve-month, and `ret_3m` already carries recent movement deliberately.
Recorded as an open parameter rather than settled forever.

> **Erratum (2026-09-06, added during implementation).** `off_52w_high` requires its window to
> be covered on the same rule as the return metrics, otherwise a five-bar security reports
> itself at its 52-week high: with fewer bars than the window calls for, "max adjusted close
> over 52 weeks" degenerates to "max of what little there is", which a short history satisfies
> trivially and reports as 0 — *at* the high — rather than as absent. The fix is D8's rule
> applied here as well as to the return metrics: a security short of the window contributes
> nothing for this metric rather than a value computed against too little data.

**D6 — Mid-rank percentile, and `higher_is_better` drives an inversion.**

```
percentile = (count strictly below + 0.5 × count equal) / n × 100
```

Ties are handled symmetrically rather than by arbitrary ordering. When
`metric.higher_is_better` is false the result is `100 − percentile`.

Nothing in this cycle sets that flag false — all four momentum metrics reward a higher number —
but the inversion is implemented and tested now. P/E arrives in cycle two, and an untested
inversion discovered then would be expensive in a way that a tested unused one is not.

> **Erratum (2026-09-06, added during implementation).** That formula satisfies the all-equal
> property section 7 asks for — every member of a flat group scores 50 — but fails the endpoint
> property the same section asks for: the minimum of a distinct group should score 0 and the
> maximum 100, and `(0 + 0.5) / n × 100` does not reach 0 for the lowest member. The implemented
> form is `(below + (equal − 1) / 2) / (n − 1) × 100`, which satisfies both at once, and a
> single-member group scores 50 under it — there is no peer to rank against, so neither
> endpoint applies.

**D7 — Peer resolution walks up from industry.** All 1,504 `security_sector` rows point at a
**level-2 (industry)** node, so reaching the level-1 sector group means following
`sector_node.parent_id`. This is not obvious from the schema and is exactly the kind of thing
otherwise discovered mid-implementation.

The peer groups already exist from the universe load: `market` at level 0 and the eleven sectors
at level 1. `metric_daily.fallback_level` therefore mirrors `peer_group.level` — normally 1,
dropping to 0 only if a sector fell below the twenty-member floor. The thinnest sector holds 49,
so that ladder is unexercised in practice and implemented anyway.

**D8 — A security that cannot be scored is absent, not zero.** `LEG` has five bars, so no window
computes. `pillar_score_daily.score` is `not null`, so such a security either gets skipped
entirely or gets a row carrying `coverage = 0` and a meaningless number.

It is skipped: no metric rows, no pillar row, no snapshot row, absent from the screen. A
zero-coverage score invites being read as "scored badly" when the truth is "not scored", and the
screen has no way to tell those apart. Measured against the loaded universe this affects 10 of
1,504 securities for `ret_12m` and 5 for `ret_3m`; a security short of *every* window is
skipped, one short of some contributes what it has and carries the lower coverage.

**D9 — The whole run is one transaction.** Deliberately unlike ingest, which committed per
security because each was independent evidence and a partial night self-healed through the
per-security window derivation.

Here a half-scored day is worse than no day: tomorrow's crossing diff would compare against it
and invent a crossing for every security that never got scored. Volume makes this free — roughly
9,000 rows a night against ingest's 2.4 million.

**D10 — `cutoff_offset` is honoured for prices, not only for fundamentals.** Bars are filtered on
`observed_at <= as_of + cutoff_offset`, not merely on `trade_date`. Cheap — one predicate — and
it is the single property that makes a later backtest mean anything, because live and backfill
runs then evaluate the identical expression.

**D11 — Reference data is seeded by migration.** `pillar` (five rows; Event risk is a flag layer
rather than a score, per `DESIGN.md`), the four `metric` rows, `scoring_logic_version` v1, and
`weight_version` v1 with `pillar_weight` `{Momentum: 1.0}`.

A migration rather than a seed command because `metric.code` must agree with the code computing
it — they change together, so they ship together. Weights are the exception the schema
deliberately allows to be tuned in the database without a redeploy; the migration only
establishes the first row.

> **Erratum (2026-09-06, added during implementation).** The migration is `019_scoring_reference.sql`;
> 018 became the MCP role. Seeding collided with six test modules that inserted `pillar
> ('quality', ...)` or `weight_version('v1')` themselves — `tests/test_reference.py`,
> `tests/test_scoring_runs.py`, `tests/test_derived.py`, `tests/test_alerting.py`,
> `tests/test_partitions.py` and `tests/test_point_in_time.py` — and all six now read the seeded
> rows instead of inserting their own.

**D12 — `as_of` is the run date, and there is no market calendar.** A weekend run produces a
snapshot identical to Friday's, which is honest: the score genuinely did not move, and no
crossing fires. Introducing a trading calendar to suppress those rows would add a dependency and
a source of drift to save a few thousand rows a year.

## 3. Conventions this follows

- Each package has a small public surface through `__init__.py`; nothing outside imports a
  submodule directly.
- Pure computation is separated from database work, as `screener.ingest` separates `parse` from
  `load`. Five of the seven modules take plain values and return plain values.
- `Decimal` throughout, never `float`. Percentiles and scores are `numeric` columns.
- All SQL identifiers lowercase; `timestamptz` never `timestamp`.
- Comments explain *why*, not *what*.

## 4. Layout

```
screener.scoring
  __main__.py    raise SystemExit(main())
  cli.py         argparse main(argv), `run` and nothing else yet
  adjust.py      raw bars + corporate actions → adjusted close series      [pure]
  metrics.py     adjusted series → the four raw values                     [pure]
  percentile.py  values within a group → percentiles, and the deciles      [pure]
  pillars.py     metric percentiles → pillar score + coverage              [pure]
  blend.py       pillar scores + weights → blended, agreement, coverage    [pure]
  peers.py       security → peer group, walking parent_id; the 20 floor
  run.py         scoring_run lifecycle, orchestration, every write
```

A new migration seeds the reference data of D11.

## 5. `python -m screener.scoring run`

> **Erratum (2026-09-06, added during implementation).** `cutoff_offset` is `'1 day 6 hours'`,
> the value the schema spec names — not restated as a parameter here, so it is worth saying
> once that this section means that value and not a different one chosen for scoring.

```
open scoring_run   as_of, cutoff_offset, logic v1, weight v1,
                   status='live', emits_alerts=false
   │
   ├─ read 13 months of bars for every active security, filtered on
   │  observed_at <= as_of + cutoff_offset          (~400k rows, one query)
   ├─ read corporate_action over the same window
   │
   ├─ adjust      → adjusted close series per security
   ├─ metrics     → up to four raw values per security; skip a security with none
   ├─ peers       → security → sector peer group, via parent_id
   ├─ percentile  → percentile per (metric, group), and eleven deciles per group
   │
   ├─ write metric_daily        raw_value and percentile side by side
   ├─ write peer_group_stat     the decile cache
   ├─ write pillar_score_daily  score, metric_count, coverage
   ├─ write snapshot_daily      blended_score, pillar_agreement,
   │                            min_coverage, worst_fallback_level
   │
   └─ close run (outcome ok)
```

`blended_score` is the weighted mean over pillars present. `pillar_agreement` counts pillars at
or above the 75th percentile — 0 or 1 while there is one pillar. `min_coverage` is the minimum
across contributing pillars. `worst_fallback_level` takes the **minimum** level across a
security's metrics, since a higher level is more specific (2 industry → 1 sector → 0 market).

`--as-of` overrides the run date for testing. Like ingest's `--today` it refuses a date in the
past, because the one-live-run-per-date exclusion constraint makes a backdated live run a
conflict rather than a convenience; historical runs are `status='backfill'`, which this cycle
does not build.

## 6. Failure behaviour

| failure | behaviour |
|---|---|
| a security has no computable metric | skipped entirely (D8); counted and logged |
| a sector falls below 20 members | that security's metrics fall back to the `market` group, `fallback_level` 0 |
| no bars visible at all under the cutoff | run fails before writing; an empty snapshot is worse than none |
| a live run already covers `as_of` | the exclusion constraint rejects it; the run fails with that stated |
| anything raises mid-run | the single transaction rolls back; `scoring_run` is left `running` as the record that it died, exactly as ingest leaves `ingest_run` |

> **Erratum (2026-09-06, added during implementation).** A failed run wedges its own date.
> `scoring_run`'s exclusion constraint is `exclude using gist (as_of_range with &&) where
> (status = 'live')` — it keys on `status`, while a run that died is recorded through
> `outcome`. So the row this section deliberately leaves at `status = 'live', outcome =
> 'running'` blocks any later live run for that date, permanently. The schema cannot express "a
> failed live run stops blocking its date": `status` permits only `live`, `backfill` and
> `experiment`, none of which honestly means "failed". Recovery is therefore an operator
> action — a failed run wrote nothing, so its row has no dependants and deleting it is safe.
> `screener.scoring.cli` prints the exact statement at the moment of failure: `delete from
> scoring_run where as_of_range = daterange('<as_of>', '<as_of + 1 day>', '[)') and outcome =
> 'running'`. Documented alongside the `python -m screener.scoring run` entry in `CLAUDE.md`,
> where an operator would look for it.

## 7. Testing

Postgres 16 for the database halves; the pure modules need nothing. Load-bearing claims,
demonstrated rather than asserted:

- **A flat price series across a 2-for-1 split scores a 0% twelve-month return, not −50%.** The
  headline test of the cycle.
- A dividend reduces the adjusted history so total return exceeds price return by the yield.
- Adjustment composes: two splits and a dividend in one window produce the product of the
  factors, in date order.
- Mid-rank percentile: a group where every value is equal gives every member 50, and min and max
  of a distinct group give 0 and 100.
- `higher_is_better = false` inverts the percentile.
- A missing metric lowers `coverage` and `metric_count` without changing the mean of those
  present.
- A security with no computable metric produces no rows in any of the three tables.
- The whole run is atomic: inject a failure between `pillar_score_daily` and `snapshot_daily`
  and assert all three tables are empty.
- A second live run for the same `as_of` is rejected by the exclusion constraint.
- `cutoff_offset` excludes a bar observed after the cutoff even when its `trade_date` qualifies.
- `blended_score` equals the momentum pillar score exactly, under `{Momentum: 1.0}`.
- Every `scoring_run` this cycle writes has `emits_alerts = false`.

## 8. Out of scope

- Fundamentals, and the four pillars that need them.
- The crossing diff, cooldown, and the Discord POST. `emits_alerts` is false precisely so that
  cycle can be built deliberately rather than inherited.
- Replacing `screener.concept` in the dashboard and the bot's chart tool. That reads
  `snapshot_daily`, which this cycle finally produces, but the endpoint and the swap are their
  own work.
- Historical `status='backfill'` runs, and the derived-table partitions before 2026 they would
  need.
- Industry-level peer groups. `fallback_level` 2 stays unexercised until a universe large enough
  to support it exists.
- Scheduling. Nothing runs this on a timer, exactly as nothing yet runs ingest.

## 9. Open parameters

- **Plain twelve-month versus 12-minus-1.** Settled at plain for consistency (D5). The forward
  log is what would settle it properly, and adding `ret_12_1m` later is one metric row plus one
  function.
- **The 75th percentile threshold for `pillar_agreement`.** Follows `DESIGN.md`'s "top quartile"
  and is otherwise arbitrary.
- **The coverage floor for alert suppression**, per `alert_rule.min_coverage`. Cannot be settled
  until more than one pillar exists; that is the alerting cycle's problem.
- **Weight version v1 is `{Momentum: 1.0}` by necessity, not by judgement.** The first real
  weighting decision arrives with the second pillar.
